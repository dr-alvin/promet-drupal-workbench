Architecture, Two-Gate Safety & Invariants

            
Key principles that guarantee 100% non-destructive rehearsals and clean developer repositories.

          


          

            

              

                
              

              

                
1. Centralized & Non-Invasive Workbench

                
The Workbench operates externally from its own directory (detected at ./). Never copy, submodule, or commit upgrade tools into client Drupal repositories. Developers can clone and run the Workbench from any location of their choice; client Drupal codebases remain completely untouched and clean.

              

            


            

              

                
              

              

                
2. Disposable Container Scans

                
During Gate 1 audits, Drush, Upgrade Status, and Drupal Rector execute inside an isolated MariaDB container (db:3306). The developer's live database is never touched prior to upgrade approval.

              

            


            

              

                
              

              

                
3. Atomic Recovery Checkpoints

                
Before any file is edited or any Composer update executes, the engine dumps pre-upgrade.sql.gz and records the pre-upgrade Git HEAD commit hash.

              

            


            

              

                
              

              

                
4. Smart Static Analysis

                
Contrib extensions follow upstream Drupal.org packaging. Contrib PHPStan is skipped (--ignore-contrib) to accelerate scans from 15 minutes to ~1 minute, focusing deep static analysis on custom code.

              

            


            

              

                
              

              

                
5. Guaranteed 1-Click Clean Rollback

                
Rollback restores pre-upgrade.sql.gz, resets the Git working tree to the pre-upgrade commit, re-runs Composer install, and validates site health with HTTP 200.

              

            


            

              

                
              

              

                
6. Strict "Keep" Decision Invariant

                
An extension can never be assigned action: "keep" if it has deprecation notices or PHPStan issues. Any extension with findings must use compatible_release or remediation.
